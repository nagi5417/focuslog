### 認証メールの送信回数制限

関連 PR: [#5 確認メールの再送](https://github.com/nagi5417/focuslog/pull/5) / [#6 送信回数制限](https://github.com/nagi5417/focuslog/pull/6)

#### 課題

確認メールが届かなかったユーザー向けに「未確認のまま再登録したら確認メールを再送する」機能を追加したところ、再送に回数制限がないことに気づいた。

- 第三者が**他人のメールアドレスで登録を繰り返すだけで**、そのアドレスにメールを何通でも送りつけられる（メール爆撃）
- 送信サービスの無料枠（Resend: 100通/日）を使い切られると、**正規ユーザーにもメールが届かなくなる**
- パスワードリセットにも同じ穴があった。さらに送信失敗時だけ画面がエラーになるため、**「エラーになるアドレス＝登録済み」と外部から判別できた**

#### 対策

確認メール・パスワード再設定メールの送信を、**同じアドレス・同じ用途ごとに「前回から1分以上」かつ「24時間で5通まで」** に制限した。

| 状況 | 画面の表示 | 実際の挙動 |
| --- | --- | --- |
| 制限内 | 「送信しました」 | メールを送る |
| 制限に達した | 「送信しました」 | **メールを送らず、トークンも発行しない** |
| パスワードリセットで送信失敗 | 「送信しました」 | 原因をサーバーログに記録する |

#### 設計判断

| 判断 | 理由 |
| --- | --- |
| **制限に達しても成功と同じ表示にする** | 制限が発動するのは送信履歴があるアドレス、つまりほぼ登録済みのアドレス。「上限に達しました」と表示すると、アドレスを入力するだけで登録の有無を調べられてしまう（アカウント列挙攻撃）。本人が制限に気づけない不便さより、登録情報の保護を優先した |
| **制限中は新しいトークンを発行しない** | トークンは発行し直すと古いものが無効になる。制限中に発行すると直前に届いたメールのリンクが使えなくなり、本人が確認を完了できなくなるため |
| **送信の前に履歴を記録する** | 送信に失敗した回も1回に数え、失敗時の連打で送信サービスに負荷をかけ続けられないようにした |
| **回数の記録に DB のテーブルを使う** | Vercel や AWS Lambda などのサーバーレス環境では、リクエストごとに別のインスタンスが処理しうるため、メモリ上のカウンターでは回数を共有できない。既存トークンの有効期限から送信時刻を逆算する案（スキーマ変更なし）も検討したが、「間隔」しか判定できず1日の上限をかけられないため採用しなかった |
| **宛先を小文字に正規化して数える** | `Victim@example.com` のように大文字小文字を変えるだけで制限をすり抜けられるのを防ぐ |
| **判定ロジックを `"use server"` ファイルの外に置く** | Next.js では `"use server"` ファイルで export した関数がすべてブラウザから呼べる Server Action になる。内部用の判定関数が外部に公開されないよう、別モジュールにした |
| **同時リクエストでの誤差は許容する** | 判定と記録の間にわずかな隙間があり、同時に送られると上限を1通程度超えうる。目的は大量送信の抑止であり、厳密に直列化する複雑さには見合わないと判断した |
| **古い履歴は書き込みのたびに削除する** | 24時間を過ぎた履歴は判定に使わない。定期実行の仕組みを追加せずにテーブルを小さく保てる |

#### 検証

- ユニットテストを16件追加した（制限の境界値、大文字小文字の正規化、制限中にトークンを発行しないこと、パスワードリセットの送信失敗時の応答など）
- テストが本当に不具合を検出できるか確かめるため、**実装を4通り意図的に壊し**（1分判定の境界 / 5通の上限 / リセット側の判定漏れ / 判定とトークン発行の順序の逆転）、それぞれ対応するテストが失敗することを確認した
- マイグレーション SQL は DB に接続しない `prisma migrate diff` で生成し、作業中に本番 DB へ誤って接続するリスクを避けた

#### 今後の課題

- **IP アドレス単位の制限**: 今回はアドレス単位の制限のため、多数の異なるアドレスにばらまく攻撃は防げない
- **メールアドレスの大文字小文字の扱い**: `User.email` の一意制約が大文字小文字を区別するため、大文字小文字違いで別アカウントを作れてしまう（送信回数は正規化して数えるため、メール爆撃自体は防げている）

### タスク一覧のセクション構成

関連 PR: [#7 タスク一覧のセクション再構成](https://github.com/nagi5417/focuslog/pull/7)

#### 課題

タスク一覧のセクションが「今日のタスク」「その他のタスク」の2つしかなく、状態が把握しづらかった。

- **期限切れが埋もれる**: 「今日のタスク」が今日期限と期限切れを同居させていた。行の色では区別できるが、放置されたタスクが何件あるか分からない
- **完了タスクが混ざり続ける**: 完了しても同じセクション内で末尾に送られるだけで、やるべきタスクと同居していた
- **「その他」の中身が曖昧**: 明日以降の期限と期限なしが同じ場所にあった

#### 対策

期限の状態ごとに分けた5セクションへ再構成し、完了したタスクは専用セクションへ移すようにした。

| セクション | 中身 | 既定 |
| --- | --- | --- |
| 期限切れ | 昨日以前が期限・未完了 | 開く（0件なら非表示） |
| 今日のタスク | 今日が期限・未完了 | 開く |
| 今後のタスク | 明日以降が期限・未完了 | 閉じる |
| 日付未設定のタスク | 期限なし・未完了 | 閉じる |
| 完了したタスク | 完了済みすべて | 閉じる |

#### 設計判断

| 判断 | 理由 |
| --- | --- |
| **セクションを保存せず、`status` と `dueDate` から都度算出する** | 「完了したら移動する」をイベント処理として実装すると、期限の変更や日付の変わり目とズレて不整合が起きる。表示のたびに算出すれば、完了で移動し、完了を外せば元のセクションへ戻る挙動が、移動処理を書かずに成立する |
| **「日付による分類」と「完了かどうか」を関数として分けた**（`toDueBucket` / `toSection`） | ヘッダーの統計は完了済みも含めて「今日期限が何件あるか」を数える必要があり、表示セクションの分類とは対象が異なるため。`toSection` は `toDueBucket` を包む形にして二重管理を避けた |
| **判定・並び替え・グループ化を純関数として `task-transform.ts` に置いた** | React に依存させないことで、日付の境界値（JST の 23:59 と翌 00:00）を固定した「今」でユニットテストできる。「今」をサーバーで確定して `nowMs` として渡す既存の設計（ハイドレーション不一致と JST ずれの回避）を踏襲している |
| **「今後のタスク」を新設した** | 「その他」を「日付未設定」に改称すると、明日以降の期限の置き場所がなくなる。セクション名と中身が一致することを優先した |
| **完了セクションは既定で折りたたむ** | 完了タスクは使うほど増え続けるため。読み込むデータ量は従来と同じ（ページは元々すべてのタスクを取得している） |
| **ヘッダーの「計測」は今日実際に計測した時間にする**（[#8](https://github.com/nagi5417/focuslog/pull/8) で修正） | 当初はタスクの累計時間を合計していたため、今日作業していなくても過去の記録が表示されていた（下記「リリース後に見つかった不整合」）。今日の判定はレポート画面と同じく計測の開始時刻で行い、画面間で数字がそろうようにした |

#### 検証

- ユニットテストを11件追加（日付境界、完了時の分類、並び替えの規則、5セクションへの振り分け）
- E2E に「期限切れのタスクを完了すると完了セクションへ移動すること」「完了を外すと元のセクションへ戻ること」を追加
- E2E が1件失敗したが、原因は**製品ではなくテストのロケータ**だった。タスク行の「『○○』を編集」ボタンのアクセシブル名にタスク名が含まれるため、`期限切れ` を含む名前のタスクがあると完了セクションを期限切れセクションと誤認していた。セクションの見出しボタンを `^期限切れ 1$` の形で厳密に一致させて解決した

#### リリース後に見つかった不整合

リリース後、タスクが1件もない状態でヘッダーが「今日 0件 / 期限切れ 0件 / 完了 0件 (0%) · 計測 418h 32m」と表示された。

実データを調べると、原因は2つ重なっていた。

1. **集計条件のズレ**: 計測は「今日期限 + 期限切れ（完了を問わない）」を合計していた一方、期限切れの件数は未完了だけを数えていた。「期限切れかつ完了済み」のタスクが、件数のどこにも現れずに計測時間にだけ入っていた
2. **計測がタスクの累計時間だった**（今回の変更以前から）: 値はタスクに記録された全期間の合計で、今日の作業時間ではなかった。該当タスクには、タイマーの止め忘れで17日間計測され続けた記録が1件残っていた

1 は私が集計範囲を「従来どおり」に据え置いたことで生まれた。表示される数字どうしの集計条件がそろっているかを確認していなかった。根本的には 2 の定義の問題なので、「計測」を今日の計測記録の合計に定義し直して解決した。

同じ「表示と集計のズレ」は**サイドバーの件数バッジ**にもあった。バッジは期限が今日以前のタスクを数えていたが、完了済みを除いていなかった。未完了が1件もないのに数字が残るため、タスク画面の「期限切れ」＋「今日のタスク」の件数と一致するよう、完了済みを除外した。

- サーバーで「開始時刻が今日・停止済み」の計測記録を集計し、計測中のタイマーはクライアントで経過時間を加算する
- タイマー停止の反映は、ストアの変更を購読して受け取る。購読はマウント後に始まるため、サーバー集計に含まれている停止を二重に数えない

#### 今後の課題

- **完了タスクの表示件数**: 現在はすべて表示している。増え続けた場合に備え、期間での絞り込みやページングが必要になる

### キーボードショートカット

関連 PR: [#9 キーボードショートカットの実装](https://github.com/nagi5417/focuslog/pull/9)

#### 課題

サイドバーに「新規タスク N」「計測 開始 / 停止 Space」「レポートへ G R」と表示していたが、**どれも実装されておらず表示だけ**だった。キー入力を受ける処理はタスク画面の検索（`⌘K`）だけで、こちらは一覧に載っていなかった。

#### 対策

| キー | 動作 |
| --- | --- |
| `N` | 新規タスクの作成を開く。タスク画面以外ならタスク画面へ移動して開く |
| `F` | **検索欄のある画面でだけ**、その画面の検索を開く（現在はタスク画面） |
| `Space` | 計測中なら停止。していなければ、直前に計測していた未完了のタスクを再開 |
| `G` → `R` | レポート画面へ移動（`G` の後 1 秒以内に `R`） |

すべて修飾キーなしにそろえ、ブラウザの操作（`⌘F` のページ内検索、`⌘R` の再読み込みなど）は奪わない。設定画面の「操作」から**ショートカットを無効にできる**。

#### 設計判断

| 判断 | 理由 |
| --- | --- |
| **検索は修飾キーなしの `F` にした** | 当初は `⌘K`、次に `⌘F` を検討した。しかし `⌘F` はブラウザのページ内検索で、奪うと利用者が使えなくなる。他のショートカット（`N` / `Space` / `G R`）が修飾キーなしだったので `F` に統一し、ブラウザとの衝突もなくした。Mac と Windows で表示を変える必要もなくなった |
| **レポートへの移動は `⌘R` ではなく `G` → `R`** | `⌘R` / `Ctrl+R` はブラウザの再読み込み。奪うと、再読み込みしようとした人がレポート画面へ飛ばされる。`G` → 文字の2段階入力は GitHub などでも使われる形 |
| **1文字のショートカットを無効にする設定を用意した** | 修飾キーなしの1文字ショートカットは、音声入力を使う人が話した言葉で誤って発動しうる。アクセシビリティ基準 WCAG 2.1.4（Character Key Shortcuts）は、無効化・割り当て変更などの手段を求めている |
| **無効にしたら、サイドバーの一覧と検索ボタンのキー表示も消す** | この改修のきっかけは「表示されているのに効かない」ことだった。無効時に表示だけ残すと、同じ問題を自分で作ってしまう |
| **設定は DB に保存する** | テーマやアクセントカラーと同じ扱いにし、別の端末でも引き継がれるようにした。ブラウザ保存だとサーバー側で設定が分からず、読み込み直後に一覧が一瞬表示されてから消える |
| **「検索欄のある画面」を画面側の登録で表す** | 検索欄を持つ画面が、表示している間だけ「開き方」をストアに登録し、ショートカット側は登録の有無だけを見る。URL を並べて判定すると、検索欄を増やすたびに判定を書き足す必要がある |
| **文字入力中・IME 変換中・ダイアログ表示中は反応しない** | 入力欄で `N` を奪うと文字が打てなくなる。IME 変換中（`isComposing`）を除外しないと、日本語入力の操作をショートカットと誤認する |
| **`Space` はボタンやチェックボックスにフォーカスがあるときは反応しない** | それらは `Space` で押下・切り替えができる。ショートカットを優先すると、キーボードで操作している人の標準操作を奪ってしまう |
| **「直前のタスク」はキーを押した時点でサーバーに問い合わせる** | クライアントの記憶に頼ると、停止後に完了にしたタスクや、別の端末で計測したタスクを正しく扱えない |
| **新規作成モーダルの開閉をストア（Zustand）に置く** | 他の画面で `N` を押すとタスク画面へ遷移する。遷移先で開くには、状態が画面遷移をまたぐ必要がある |
| **「タスク画面を離れたら閉じる」は URL の変化で判定する** | 当初はタスク画面のアンマウント時にリセットしていた。しかし開発環境の React（Strict Mode）はマウント直後に後処理を1回挟むため、他画面から「開いて」遷移してきた直後に打ち消されていた |

#### 検証

- ユニットテスト: ショートカットのコンポーネントテスト23件（各キーの動作、反応してはいけない状況、無効時、`G`→`R` の時間切れ、開閉状態のリセット）、設定スイッチのテスト、検索の登録ストア・再開処理のテスト
- 判定を意図的に外し（入力中 / IME 変換中 / Space のフォーカス / `G`→`R` の時間制限 / 修飾キー付きの除外）、それぞれ対応するテストが失敗することを確認した
- E2E（実ブラウザ）: 7件。途中で次の3つを学んだ
  - **ユニットテストでは見つからない不具合を E2E が検出した**。ユニットテストは画面遷移をモックしていたため、遷移後に開閉状態が打ち消される問題を再現できなかった
  - **「何も起きない」ことを確かめるテストは、キー入力の受け付けが始まる前に押すと、実装が間違っていても通ってしまう**。先に効くキーで受け付けを確かめてから押す形にした
  - **設定を元に戻す後片付けが、表示の変化（楽観的更新）だけを見ていた**。保存が終わる前にテストが終了してリクエストが中断され、後続のテストがショートカット無効のまま実行されて失敗した。保存完了後にだけ起きる変化（サイドバーの一覧の再表示）を待つ形に直した

#### 関連して修正した問題（セキュリティ）

`Space` の再開処理の土台として計測開始の処理（`startTimer`）を読んだところ、**タスクの持ち主を確認していなかった**。任意のタスク ID を渡せば、他人のタスクに計測記録を紐づけ、そのタスクの計測時間を水増しできた。自分のタスクでなければ拒否し、既存の計測も止めないように修正した（別コミットに分離）。

#### 今後の課題

- **開発・E2E 用のデータベースを本番と分ける**: 作業中に、ローカル開発と E2E が本番のデータベースに接続していることが分かった。E2E のテスト用データが本番に作られ、今回のマイグレーションも本番に先に適用する必要があった。Neon のブランチ機能などで開発用のデータベースを分けたい

### 停止したタイマーが復活する不具合

関連 PR: [#10 サイドバーのバッジとタイマー停止の修正](https://github.com/nagi5417/focuslog/pull/10)

#### 課題

E2E の「Space で計測を停止する」テストが、3回に1回ほど失敗した。単体で動かすと通り、全体で動かすと落ちる。

#### 原因

推測で直さず、失敗した時点の状態を調べた。キー入力は届いていて（`defaultPrevented` が true）、サーバーへの通信も成功しているのに、タイマーが止まっていない。タイマーの状態を画面から取り出すと、**停止の処理は実行されている（停止回数が増えている）のに、計測中のタスクが元のまま残っていた**。

原因は `TimerBar` の復元処理だった。サーバーが持っている「計測中のタイマー」を復元する処理が、計測中のタスクの変化をきっかけに何度も動く作りになっていた。

1. 計測を開始すると `revalidatePath` で画面が再取得され、「計測中のタイマーあり」という情報が渡ってくる
2. 停止して計測中のタスクが空になる
3. **その変化をきっかけに復元処理が再び動き、1 の情報でタイマーを復活させる**

停止ボタンでも同じ競合が起きうる。再取得と停止のどちらが先に届くかで結果が変わるため、失敗したりしなかったりしていた。

#### 対策

復元は「ページを開いた最初の一度だけ」行うようにした。停止後に復元処理が動かないため、競合しなくなる。

#### 検証

- 停止後に「計測中」の情報が渡ってきても復元しないことを `TimerBar` のテストで固定した。修正前のコードに戻すとこのテストが失敗することも確認済み
- E2E は、テストの待ち時間を延ばしても直らなかった。**待ち時間の調整で誤魔化さず、原因を突き止めたことでテストが安定した**
